# v0.25.1 — Option+Arrow moves by word in the terminal again

- **Option/Alt+Left and Option/Alt+Right jump a word** — xterm dropped the Alt-to-word-motion translation it had carried since 2016 and now emits the bare modified-arrow sequence `\e[1;3D`, which zsh's emacs keymap never binds. The line editor beeped and the trailing `D` self-inserted, so the chord typed a letter instead of moving the cursor. The terminal now sends `\eb` / `\ef`, which every line editor already understands.
- **Ctrl+U deletes back to the start of the line** — zsh binds `^U` to kill-whole-line, which takes the text ahead of the cursor with it. Sending a negative argument ahead of kill-line (`\e-` then `^K`) is readline's behaviour and reads identically under bash and zsh, so no shell rc file has to change for it.
- **Ctrl+K is untouched** — forward kill-line is already the default in both shells, so it needed no rewrite and got none.
- **Full-screen programs keep the standard sequences** — the rewrite applies only while the shell prompt is on screen. On the alternate buffer, Ctrl+U is still half a page up in vim and less, and an escape-prefixed word motion would have dropped vim out of insert mode.
- **Chords match on physical key position** — `event.code` rather than `event.key`, because macOS composes Option and a letter into a symbol.

No storage format change and no server change; the fix is entirely in the browser-side terminal.
