# v0.25.0 — match counts everywhere, and a bundle shaped for a long link

Every find surface now reports how many matches it found, the diff's find box stops sliding off the top of the pane, and the front-end payload is split so a distant browser can fetch it in parallel.

- **Every find box counts its matches** — `1 of 118` beside the query field, in the markdown editor, in code tabs, and in both columns of a split diff, including buffers never saved to disk. One CodeMirror view plugin registered three times rather than three overlays: the panel is built and torn down by the search extension on its own schedule, and a split diff has two of them alive at once, so anything anchored from outside would have to track all of it. Enumeration stops at 20,000 and reports `20000+` instead of walking a huge match set on every keystroke.
- **The diff's find box stops scrolling away** — CodeMirror makes the panel sticky in its own base theme, but `@codemirror/merge` gives each column wrapper `overflow: hidden`, and `hidden` makes a box a scroll container — which is what `position: sticky` measures itself against. The panel was pinning itself to the top of a box as tall as the whole file, so it scrolled off with the text and left the find field somewhere above the viewport. `overflow: clip` clips identically without being a scroll container, so the panel now measures against the merge container, the element that really scrolls.
- **The diff gets a tick rail** — matches from both columns mark the single scrollbar a split diff has, amber for a match and orange for the one the cursor is on, the same reading as the code editor's rail. Positions convert through the merge container's scroll range rather than each editor's own, so they are correct in split and inline mode and are independent of scroll position by construction.
- **The front-end ships as eight parallel chunks instead of one 827 kB file** — identical total bytes, grouped by dependency layer so the browser fetches them side by side and an app-code edit no longer invalidates the cached vendor chunks. Two rules in `server/vite.config.mts` stay deliberately narrow and say so in place: naming `@codemirror/lang-*` broadly, or `@lezer/*` broadly, or adding any catch-all, drags roughly 130 lazily-loaded grammars plus mermaid and katex into a statically loaded chunk — about 2 MB that nobody downloads today.
- **A boot skeleton paints from the first response** — inline markup and CSS in `index.html`, no asset required. It retires itself with no script involved: `#app` stays empty until the app mounts, so a sibling `:not(:empty)` rule hides the skeleton once there is something real behind it. Over a long link the document arrived seconds before anything appeared, and a blank page is indistinguishable from a broken one.
- **Preview find reads like the others** — `3 of 56` rather than `3 / 56`, and nothing at all until a query is typed.
- **The eight pre-resolved fenced-code grammars stay eager on purpose** — they now travel in their own parallel chunk instead of inside the main one. Making them lazy would re-break the v0.5.0 fix: language-data's lazy descriptors leave an already-parsed fence plain, and the re-decorate after load is unreliable for fences this stack has already parsed.

No storage format change; tabs remembered under v0.24.x restore unchanged. The transport tuning these two payload changes were sized against — BBR and a wider initial congestion window on the machine serving this over a long-haul link — lives on that host, not in this package.
