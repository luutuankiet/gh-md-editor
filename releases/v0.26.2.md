# v0.26.2 — the merge view stops losing your place

A follow-on to the last release, which taught the Git Graph tab to remember
what it was showing. The same audit, applied to the merge view, turned up a
gap: coming back to a half-finished conflict resolution put you somewhere you
had not been.

## What was wrong

The merge view shows a file four ways at once — the version in this branch,
the common ancestor, the version being merged in, and the working copy you
edit. Switching to another tab destroys all four and rebuilds them from
scratch when you come back, which is the shell's normal behaviour and the
reason tabs are cheap.

The working copy pane already came back where you left it: it is a full code
editor, and code editors here remember their position as a line number plus
the offset inside that line. The other three did not come back at all. Neither
did the conflict counter.

So returning to a file where you were working through the third of four
conflicts gave you: the toolbar announcing "Conflict 1 of 4", the three
reference panes scrolled back to the top and highlighting the first conflict,
and the pane you type in sitting exactly where you left it, next to the third.
One tab, disagreeing with itself about where you were.

## What changed

Two things are now remembered per merge tab, alongside the word wrap setting
that already was.

**Where the reference panes were scrolled.** Stored as a fraction of the
scrollable height rather than as a pixel offset, because a fraction is already
the coordinate those three panes use to scroll each other — the three sides of
a conflicted file are different lengths, so exact line alignment was never on
offer and one number is what brings all three back together.

Restoring it retries for up to a second and a half rather than being applied
once. A code editor reports no scrollable height at all until it has laid the
document out, and a fraction of nothing is a silent scroll to the top — which
looks exactly like the position never having been saved.

**Which conflict was selected.** The counter, the highlight in all four panes
and the up/down stepping all key off this, so restoring it is what makes the
reference panes agree with the working copy about which conflict is being
worked on. It is applied after the file loads rather than when the tab mounts:
a tab that has only just appeared is looking at an empty document, and the
guard that keeps the counter from pointing past the last conflict would have
folded any remembered index straight back to the first.

The working copy pane is deliberately left alone. It restores itself from a
line anchor, which keeps pointing at the same text after a word wrap or font
size change — a fraction does not. Where two mechanisms overlap, the more
accurate one wins.

Both values ride in the same per-workspace store as the other per-tab
settings, so they survive a reload as well as a tab switch, and they cost
nothing for anyone who never opens a merge.

## Unchanged

No behaviour changes outside the merge view. The lockstep scrolling between
the reference panes, the accept buttons, staging on Complete Merge, and the
notice shown when a file's conflict has already been resolved elsewhere all
work as they did.
